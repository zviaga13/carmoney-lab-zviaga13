# План MILEAGE: пробег авто > 400 000 км → review

**Задача:** MILEAGE (ДЗ.1) · **Статус:** черновик, на утверждение заказчиком · **Дата:** 2026-10-05

> Целевой путь по задаче — `docs/plan/plan_MILEAGE.md`; текущие permissions запрещают
> правку `docs/`, поэтому финальная версия сохранена здесь. Черновик в
> `docs/plan/plan_MILEAGE.md` уже точен (проверен по коду 05.10.2026); отличия этой
> версии от него: подсказка `unset` для кейса «пробег отсутствует» и новый Вопрос 1
> про решение риск-менеджмента (AGENTS.md §5), остальные вопросы перенумерованы 2–7.

**Правило:** если пробег не больше 400 000 км — решение без изменений; иначе решение `review`.

Опирается на `docs/setup/code_map.md` (раздел «Куда встанет правило», строки 74–102)
и отчёт scout от 05.10.2026 (все строки перепроверены по коду 05.10.2026). Место правки —
`DecisionEngine`: правило меняет вердикт, а не валидность заявки. Валидационная граница
`vehicle.max_mileage_km = 500 000` (422) остаётся без изменений; новый порог — порог
решения, сосуществует с ней.

Допущения по умолчанию (нужно подтверждение, см. «Вопросы заказчику»):

- «не больше 400 000» включает равенство: понижение только при `mileage > 400000`
  (ровно 400 000 — без понижения);
- правило понижает только `approve` → `review`; `review` остаётся `review`,
  `reject` остаётся `reject` (высокий пробег не смягчает решение).

`mileageReviewAboveKm = 400000`; LTV-зона фиксируется параметром провайдера.

Граничные значения (каждая строка отдельно):

- пробег **399 999**, ltv 50.0 → `approve`

## 4. Риски

1. **Существующая проверка `max_mileage_km`** (`ApplicationValidator.php:43-46`, 500 000, 422) — главный риск: случайно «поправить» валидатор до 400 000 или заменить одну границу другой. Тогда заявки с пробегом 400 001–500 000 начнут получать 422 вместо `review`. Границы обязаны сосуществовать: 0–400 000 — обычный поток; 400 001–500 000 — `review` при LTV-approve; > 500 000 — 422. AGENTS.md запрещает менять пороги в `rules.php` ради зелёного `make test`.
2. **Off-by-one на границе**: «не больше 400 000» = ровно 400 000 ещё без понижения, условие строгое (`>`). Ошибка знака даст `review` на 400 000 — противоположный бизнес-результат (Вопрос 3).
3. **Ломающее изменение сигнатур**: все места создания и вызова — `AppFactory.php:37`, `AssessmentService.php:33`, `DecisionEngineTest.php:17,23`, `AssessmentServiceTest.php:27`. Пропущенное место = `ArgumentCountError` (по отчёту scout вызовов вне репозитория нет). Шаги 2–4 и обновление тестов должны приземлиться одной правкой.
4. **Семантика reject + высокий пробег** не определена формулировкой: если «иначе решение review» понимать буквально, reject надо перезаписывать review. План по умолчанию этого не делает; реализация без ответа заказчика (Вопрос 2) может потребовать переделки.
5. **«Пустой пробег» через API**: пустая строка сегодня превращается в 0 и проходит валидацию (`ApplicationValidator.php:43`). Если заказчик ждёт 422 и для пустой строки — это отдельная правка валидатора, в план не входит; молчаливое текущее поведение может удивить (Вопрос 4).
6. **`DecisionEngineTest.php` под особым режимом AGENTS.md §5** (добавление правил в этот файл — только с разрешения человека). Утверждение этого плана считается разрешением; без него кейсы выносятся в новый файл `tests/Unit/DecisionEngineMileageTest.php`.
7. **Комментарии правил уже расходятся с кодом**: `rules.php:39-41` и `DecisionEngine.php:7-12` описывают границу `LTV <= approve_max -> approve`, а код использует строгое `<` (LTV ровно 60.0 даёт `review`, `code_map.md:64-66`). При обновлении docblock'ов легко продублировать или расширить расхождение: новый комментарий должен описывать фактическую схему с пробегом, а переписывать формулировку LTV-границы без отдельного решения нельзя (Вопрос 7).
8. **Тесты читают реальный `rules.php`** (`AssessmentServiceTest::setUp`): переименование или удаление ключа `mileage.review_above_km` уронит сборку тестов на конструкторе — это желаемое сигнальное поведение, но требует синхронной правки конфига и тестов.
9. **Демо-данные**: в `db/seed.sql` пробеги 20 000–296 000 — ни одна учебная заявка не станет `review` из-за нового правила; для демонстрации нужны новые сиды, в план не входят.

Не входит (out of scope):

- **Фронтенд** — решение приходит из API, UI не меняется (по отчёту scout порогов пробега в HTML/JS нет).
- **БД** — колонка `vehicles.mileage_km INT UNSIGNED` (`db/schema.sql:22`) вмещает все значения; schema и seed не меняются.
- Задача **LOAN-12** (`ltv_by_age`), изменение `max_mileage_km`, правка формулы или границ LTV.
- **Feature/HTTP-тесты** — `tests/Feature/` пуст, инфраструктуры нет; поведение 422 покрыто юнит-тестами валидатора и сервиса.
- **Обновление `docs/setup/code_map.md`** — строки 74–113 («на решение пробег не влияет») устареют; обновление — отдельный шаг по желанию заказчика.
